# M6 第二批：段落缩进

## 实施前白盒模型

2026-09-07：继续首期方案第 10 节，补齐普通段落缩进；M5 保持暂缓。沿用 React 17、JS/JSX、AntD 5、Zustand、Rsbuild 和两套风格规范。

- 正文由 Tiptap 持有，段落/标题新增 `firstLineIndent` 与 `leftIndent` 数字属性，缺失时为 0。首行为 0–4、左侧为 0–8 整数，单位为段落字号的 em；界面称字符，不依赖文字数量或页面缩放。
- 独立 AntD Select 直接提交命令；不在 React/Zustand 缓存正文属性。选区读取当前段落，跨段选择批量修改，异值显示混合。保留列表层级缩进原有命令。
- 适用于文字选区和光标所在段落/标题，含列表、引用和表格内段落；节点和单元格矩形选区、代码块不可操作。选区终点恰在下一段开头时不修改该段。
- 命令先检查可编辑、组合输入、参数白名单和范围，再按差异提交一个事务；相同值不标脏，不制造空历史。一次设置可撤销，Enter 分段按 Tiptap 既有属性继承规则处理。
- HTML 以 `text-indent` 和 `margin-left` 的 em 表达，解析与粘贴仅接受本批范围内整数 em。格式刷复制两项属性，普通来源可清除目标缩进。
- 保存、文件导入和输出共用 schema/HTML 路径。新程序读取旧文件时补默认值，文件版本暂不变；旧程序严格校验未知属性，不能读取新增缩进属性的文件，不宣称双向兼容。
- 无后端请求、额外定时器/监听或异步状态；生命周期沿用编辑器实例与现有保存收口。

扩展属性依照 [Tiptap 官方扩展文档](https://tiptap.dev/docs/editor/extensions/custom-extensions/extend-existing)，首行布局依据 [MDN text-indent](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-indent)。

## 结果

已完成。工具栏新增首行 0–4 字符、左侧 0–8 字符两个 AntD Select。支持混合状态和批量修改；与列表层级按钮分别命名。属性跟随段落/标题，Enter 分段继承，格式刷同步复制，设置 0 可还原。

新程序可读取旧文件；旧程序不能读取携带新增属性的文件。没有依赖变更、存储表变更或后台任务。此阶段文件协议尚未发布，沿用 schemaVersion 1 的属性扩展与严格未知属性拒绝策略。

## 风格与白盒审计

本轮新增/修改代码及必要调用链确认偏差为零，符合 `$qucm-code-style`；同步执行 `$frontend-code-style`。继承具名组件、模块 SCSS、双引号、无分号与局部命令写法。React 17、AntD 5、Zustand、Rsbuild 以用户明确选择为准。

`getIndentParagraphs` 同时供命令与工具栏读取，避免两处选区规则分叉；`parseParagraphIndent` 同时供扩展解析与粘贴白名单使用。正文状态只在 Tiptap 内，派生的 mixed 不落盘；不存在需额外清理的 effect、监听或定时器。文件属性验证仍拒绝未知字段和越界值。

## 原理问题与解释

1. 为什么首行缩进不用空格补齐？空格属于正文内容，会影响查找、复制和换行；text-indent 只描述段落首行布局，保存和输出可保留语义。
2. 为什么两个下拉框不各自保留 useState？选区、撤销、格式刷都能改变属性；直接订阅当前事务状态可避免输入控件显示旧值。
3. 为什么选区终点在下一段开头要排除该段？文字选区采用半开范围，浏览器拖选上一段时可能把终点放在下一段起点；直接按遍历结果写入会误改未选文字的段落。
4. 为什么能力查询和相同值设置都不提交节点替换？能力查询只决定按钮可用；无差异替换仍可能生成事务步骤，导致无意义保存和撤销记录。
5. 为什么 HTML 和粘贴共用解析规则？序列化生成 em；若粘贴另行接受百分比或像素，就会把不同单位当成字符数量。共用白名单保证往返稳定并拒绝越界值。
