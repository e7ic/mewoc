# 局域网 HTTP 访问

2026-09-08 按用户要求重启生产预览，命令为 `pnpm preview --host 0.0.0.0 --port 4180`。本次物理网卡地址为 `172.18.0.141`，地址随网络配置变化；未修改默认回环监听配置。

## 修复与验证

首次通过局域网 HTTP 打开时显示「文档未能打开：crypto.randomUUID is not a function」。本地回环地址没有暴露该问题。新增 `tests/lan-access.test.js`，模拟仅有 getRandomValues 的 crypto 接口，运行真实新建文档链路，修复前稳定报相同错误。

统一在 createId 中使用 crypto.getRandomValues 生成 UUID v4；新建文档、会话切换、图片、附件及便携文件导入使用相同入口。保留原 ID 格式，不改已有文档或资源身份，不增加依赖、全局补丁或弱随机数回退。

- Node 18.20.6 下 118 / 118 项测试、lint、生产构建、git diff --check 通过。新增用例同时验证缺少 randomUUID 时创建文档、读取附件、导入文件，以及附件原始内容和不同 ID 保留。
- 重启后的生产包经本机浏览器访问 `http://172.18.0.141:4180/`，实际完成打开、新建会话、输入标题和正文、手动保存，显示「已保存到此浏览器」，警告和错误日志为空。
- 本机验证使用实际局域网地址；未借用另一台物理设备，不把其他设备的防火墙或网络隔离状态计为已验证。文档仍保存在各浏览器的 IndexedDB 中。

## 风格与原理核对

本次新增及修改代码符合 qucm-code-style 与 frontend-code-style，未发现确认偏差。现有技术栈、文档契约和状态所有权保持不变，公共函数只集中五处共享的 ID 生成行为。

1. **为什么监听全部网卡还不够？** HTTP 页面可以取得，但应用启动调用了当前访问源没有提供的 API，必须验证编辑器实际打开和保存。
2. **为什么使用 getRandomValues？** 它提供浏览器安全随机字节，并可用于普通 HTTP；设置 UUID v4 的版本位和变体位后继续匹配现有文档 ID 契约。
3. **为什么修复所有 ID 入口？** 仅修复首页会让附件、新建会话或导入稍后再报同样错误；统一入口避免后续操作仍依赖 randomUUID。
